# 切换账号踩坑复核清单

[返回入门说明](../README.md) · [DeepSeek 与定时任务](deepseek-and-troubleshooting.md)

核对日期：2026-10-20。本页结合历史 Gemini / Antigravity 对话、当时保存的工具日志及当前配置说明整理。只公开通用结论，不上传原聊天、私人截图、机器路径或公司配置。

**“历史日志确认”只表示当时遇到过，不表示所有版本都会发生。旧 AI 回答的自信程度不算验证证据。**

## 1. 账号切回来了，模型也要对得上

有过这样的顺序：从 DeepSeek 切回 ChatGPT 登录账号，但旧聊天还选着 DeepSeek 模型，于是客户端提示这个模型不支持该登录方式。换成官方模型后，又因为旧聊天格式不兼容而报另一个错。

这其实是两个问题，不要看到第二个错误，就以为刚才的账号根本没切成功。

**先做什么：**完全重开客户端，核对账号和模型；再新开无敏感资料的聊天做小测试。公开版切回官方账号会移除根配置里的第三方模型引用，但不能保证旧聊天、单独指定模型的定时任务或其他切换工具也同步改变。

## 2. 旧聊天和定时任务：这些报错确实出现过

| 看到的关键词 | 历史排查确认了什么 | 普通用户先怎么做 |
| --- | --- | --- |
| `array_above_max_length`，提示数组最多 0 项却收到 1 项 | 切回官方模型时，请求中的某条旧思考记录不符合接口检查；不是简单重登就能修好 | 保留旧聊天，先交接到新聊天；不要把一切归因于账号余额 |
| `422`、`missing field call_id` | 当时 DeepSeek 请求日志明确提示旧工具结果缺少关联编号，定时任务因此失败 | 先确认该任务是否接着旧聊天运行；不要连续重跑会发消息、改数据或付费的任务 |
| `invalid_id_prefix`，要求以 `msg` 开头，实际是 `fco_` | 之前把旧工具结果转换成消息时沿用了旧编号，后来切回官方模型又触发检查 | 这是历史迁移的连锁问题，不能只改一个报错字段就宣称永久兼容 |
| `remote compact task`、`input[…].name`、`string does not match pattern` | 自动整理旧聊天时，有旧工具名包含不被接受的双冒号 `::`，请求被拒绝 | 新聊天正常不代表旧历史已修复；不要盲删插件、重装客户端或批量替换所有工具名 |

这里的“整理”指客户端把很长的对话交给模型做摘要。有时普通消息还能发，到整理这一步才暴露旧格式问题。

**公开版能做什么？** `doctor` 只检查有限的侧边栏索引，`doctor --apply` 只在备份后调整已知索引。它不会改写思考记录、工具结果、消息编号或工具名称，不能拿来保证修好上面四类错误。

如果确实要修旧历史，应由熟悉格式的人单独处理：完全退出 → 备份原记录和相关索引 → 只处理已确认的问题 → 校验工具调用与结果的对应关系 → 用目标客户端复测。不把“转换成用户发言”当通用无损修复，因为记录原本的角色和含义也很重要。

## 3. 一直重连，不等于一定是账号坏了

历史日志里确实出现过 `falling back to HTTP`：客户端换了一种通信方式继续请求。它能支持“当时发生了连接回退”，**不能单靠这一行证明唯一原因是代理、共享账号、长思考或服务端算力**。

看到重连 1/5～5/5、`stream disconnected`、`request timed out`、`Upstream service temporarily unavailable`，先按这个顺序查：

1. 保留最后的完整错误，而不只是“第几次重连”。格式错误、断流和容量提示不是同一个问题。
2. 看本轮是否已经写文件、发消息或开了付费任务；不要狂按重发制造重复动作。
3. 用短的新聊天小测试，与原长聊天区分。需要开新聊天时先做交接，不承诺立刻秒回。
4. 由懂网络的人检查客户端版本、系统代理、网络路径和中转日志；一次只变一个条件再比较。
5. 某次等待后恢复、降低思考档位后变快，都是现象，不能反推隐藏的限流规则已经被证实。

### “关闭 WebSocket 就能解决”能照抄吗？

不能。WebSocket 可以简单理解为一种长连接通信方式，HTTP 流是另一种方式；它们的握手、代理和超时表现可能不同，但后者也可能断流。

- 对自定义 API 提供方，官方配置参考有 `supports_websockets` 字段。只有确认故障与此相关、目标版本支持时，才考虑由懂配置的人备份后测试，不能宣传为万能开关。
- **不要把官方内置的 `openai` 渠道当成自己的中转配置来覆盖。**历史排查中确实有添加对应配置块后重启报错、随后撤回的记录。公开版为自己的渠道使用不同名称，不要求你覆盖官方渠道。
- 当前本机 CLI 的功能列表把 `responses_websockets` 和 `responses_websockets_v2` 标成已移除，把 `respect_system_proxy` 标成开发中。不要把旧帖子里的命令当作所有版本都可用、必然生效的修复；应在同事自己的版本上核对。
- 改系统代理、开启虚拟网卡模式或设置代理环境变量会影响流量去向，不能为了这个工具就无提示地全局开启。Mac 终端里的环境，也不等于从 Dock 打开的桌面软件必然继承。

技术人员可核对[当前官方配置参考](https://developers.openai.com/codex/config-reference/)。本页不提供“一键彻底解决所有重连”的脚本。

## 4. “模型容量已满”不能靠换名称解锁

`selected model is at its capacity` 只能作为服务端返回的容量提示处理。不能直接断定“某个订阅账号坏了”，也不能凭感觉编造并发阈值、隐形额度或后台算力规则。

中转如果仍使用同一批上游账号，就不应假定它是完全独立的容量池，更不代表有企业级服务保证。让服务提供方核对实际路由、权限、错误和账单；本工具不会创造额外额度。不得承诺“充值就无限可用”“一定不会风控”。

## 5. 两个切换工具，可能各自覆盖对方的设置

如果还在使用 CC Switch、Codex++ 或其他管理工具：

- 先决定由谁管理当前配置，不要让几个工具轮流自动写同一个文件。
- 备份后再改；重启后复核一次。主配置、某个独立配置、某个旧聊天的选择，可能不是同一层。
- 命令行里成功请求某模型，不等于桌面端选择框已更新；桌面端有名字，也不等于服务商实际把请求转给了那个模型。
- 不要因为示例里的模型能用，就替同事预设所有模型、所有思考档位都能用。

## 6. 长聊天和缓存：省钱不能压过可用性

旧缓存讨论里有按单日截图给客户端排“最高命中率”的结论，也有“继续长聊天就一定接近满命中”的说法；这些没有同条件对照实验，不作为本仓库结论。

客户端怎样组织材料（有时叫 harness）、实际输入的重复程度和服务端规则都会影响缓存。保持有用背景相对稳定、同一任务连续处理是合理尝试，但不能承诺具体提升幅度，也不是用户能控制全部后台材料。

任务方向变了、长聊天越来越慢或不断整理失败，就做一份交接开新聊天。不要为保缓存强留几十兆历史，也不要假定新聊天会“完整自动记得一切”。交接可用下面的简单模板：

> 我们在做什么：……；已经确认：……；还没确认：……；相关文件：……；下一步：……。请先读取必要文件，不要重跑已完成的付费任务，也不要重复发送消息。

缓存规则和计费以[DeepSeek 官方说明](https://api-docs.deepseek.com/guides/kv_cache/)及实际响应为准；本工具不排名客户端，也不测量你的真实缓存命中率。

## 7. 不要把“有修复脚本”说成“已经全解决”

这次复核找到的是历史故障证据和部分历史修改，不是对所有旧对话重新跑了一遍。过去 AI 回答里的“100% 无损”“永久杜绝”“秒回”“任何厂商无缝兼容”都不能作为验收结论。

公开版的 Windows/Mac 自动测试验证虚构数据下的切换、备份、有限索引修复和安装入口；不保证你自己的所有旧聊天、插件、定时任务及 API 都通过。求助时只提供脱敏错误、客户端版本、账号类型和是否新聊天也失败，不要上传 Key、原始聊天或完整数据库。
